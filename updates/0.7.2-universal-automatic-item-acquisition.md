# 0.7.2 — Universal Automatic Item Acquisition

Release `0.7.2` menambahkan subsystem acquisition universal yang memisahkan kebutuhan item dari koordinasi bot, sehingga proses pengambilan item dapat diatur ulang sebagai policy runtime yang deterministik, dapat dikonfigurasi, dan siap dipakai dalam dashboard.

## Perubahan utama

- Ekstraksi logika acquisition dari coordinator menjadi service terpisah yang dapat digunakan ulang oleh runtime, API, dan dashboard.
- Policy acquisition didefinisikan sebagai settings runtime dengan validasi kuat untuk kedalaman pencarian, subtasks, attempt, jarak, serta mode pemenuhan item.
- Prioritas pengambilan mengikuti urutan deterministik: inventori → storage → fleet → craft → smelt → collect → gagal.
- Sistem memeriksa ketersediaan sumber yang paling sesuai sebelum memulai subtask, tanpa mengganggu mekanisme koordinasi yang sudah ada.
- Tool preservation dan partial fulfillment dapat diaktifkan atau dinonaktifkan sesuai kebutuhan produksi dan keamanan bot.
- Dashboard settings menambahkan panel khusus untuk Universal Automatic Item Acquisition agar policy dapat diubah tanpa edit file konfigurasi.
- API runtime menyediakan endpoint `PATCH /api/v1/settings/acquisition` dan status acquisition yang konsisten dengan `health` dan `status` aplikasi.

## Policy default

Policy default yang diterapkan:

- `enabled: true`
- `maxDepth: 8`
- `maxSubtasks: 32`
- `maxAttempts: 3`
- `maxDistance: 2000`
- `storageFirst: true`
- `allowFleet: true`
- `allowCraft: true`
- `allowSmelt: true`
- `allowCollect: true`
- `allowPartial: false`
- `toolPreservation: true`

Semua nilai tersebut dapat diubah dari dashboard Settings atau melalui konfigurasi runtime.

## Arsitektur acquisition

Subsystem acquisition berfungsi sebagai layer yang memetakan kebutuhan item ke solusi paling aman dan paling relevan. Dalam praktiknya, service ini memvalidasi permintaan, menentukan sumber yang tersedia, menyiapkan subtasks sesuai strategi, dan memutuskan kapan item dianggap terpenuhi, gagal, atau butuh fallback ke sumber lain.

Alur utama:

```text
REQUIREMENT → NORMALIZE → VALIDATE → RESOLVE SOURCE → PREPARE SUBTASK → EXECUTE → VERIFY RESULT
```

Resolver sumber bersifat incremental: ia akan mencoba inventory lokal, storage terdaftar, donor fleet, craft, smelt, dan collect sesuai kebijakan yang aktif. Jika tidak ada jalur yang valid, maka requirement akan ditolak dengan status yang eksplisit agar operasional tetap aman dan dapat diaudit.

## Endpoint dan dashboard

Endpoint yang relevan untuk release ini:

- `PATCH /api/v1/settings/acquisition`
- `GET /api/v1/dashboard/snapshot`
- `GET /api/v1/settings`

Dashboard Settings menampilkan:

- status acquisition aktif/nonaktif
- parameter kedalaman dan subtasks
- jumlah attempt dan batas jarak
- toggle source allowance dan tool preservation
- tombol apply settings untuk menerapkan policy runtime tanpa restart aplikasi

## Verifikasi release

- Service acquisition diuji melalui integrasi runtime dan validasi konfigurasi.
- Endpoint settings acquisition diverifikasi melalui API flow yang terhubung ke application container dan health layer.
- Dashboard settings dan status acquisition diperiksa melalui snapshot runtime.
- Seluruh suite test yang dijalankan pada saat release dibuat menghasilkan 94 passing, 0 failing.

## Scope

Release ini fokus pada pembuatan sistem acquisition universal yang reusable, aman, dan mudah diatur. Fitur autonomous item collection yang lebih tinggi, manajemen prioritas heuristik yang lebih kompleks, dan integrasi produksi multi-fleet tetap berada di milestone berikutnya.
