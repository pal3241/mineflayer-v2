============================================================
1. TUJUAN 0.7.1
============================================================

MineHive 0.7.1 berfokus pada recovery item ketika bot mati.

Sistem tidak boleh langsung mengambil semua item yang jatuh.

MineHive harus dapat menjawab:

"Apakah item ini layak diambil kembali?"

Contoh:

Bot mati membawa:
- diamond x8
- iron_ingot x64
- oak_log x32
- dirt x64
- rotten_flesh x12

Hasil evaluasi:

diamond x8
=> REQUIRED

iron_ingot x64
=> REQUIRED

oak_log x32
=> OPTIONAL

dirt x64
=> IGNORE

rotten_flesh x12
=> IGNORE

Recovery bot cukup memprioritaskan item yang benar-benar bernilai.

============================================================
5. DEATH DROP MEMORY
============================================================

Ketika bot mati, buat temporary short-term memory:

type:
DEATH_DROP

Contoh:

{
  "type": "DEATH_DROP",

  "memoryType": "SHORT_TERM",

  "deadBotId": "courier-2",

  "worldKey": "localhost:25565",
  "dimension": "overworld",

  "position": {
    "x": 421,
    "y": 64,
    "z": -92
  },

  "relatedTransferId": "transfer-182",

  "assignedBotId": null,

  "status": "PENDING",

  "despawnBudgetTicks": 6000,
  "estimatedLoadedTicks": 0,

  "recoveryAttempts": 0,

  "createdAt": "..."
}

DEATH_DROP bersifat operational memory.

Memory ini dihapus jika recovery sudah:
- selesai
- gagal permanen
- item sudah dipastikan despawn
- hasil partial sudah direkonsiliasi

============================================================
6. ITEM DESPAWN
============================================================

Default dropped item Minecraft memiliki umur sekitar:

6000 game ticks
≈ 5 menit

PENTING:

Jangan hanya memakai:

Date.now() - deathTime > 5 menit

untuk membatalkan recovery.

Timer item bergantung pada chunk / entity ticking.

Jika chunk unload, timer item dapat berhenti.

Karena itu konsep yang digunakan:

DESPAWN BUDGET

despawnBudgetTicks = 6000

estimatedLoadedTicks = perkiraan tick saat death chunk aktif

remainingTicks =
despawnBudgetTicks - estimatedLoadedTicks

============================================================
7. CONTOH DESPAWN BUDGET
============================================================

Bot mati.

Initial:

despawnBudgetTicks = 6000

Death chunk loaded selama:

1200 ticks

Remaining:

4800 ticks

Kemudian chunk unload selama 10 menit.

Remaining tetap diperkirakan:

4800 ticks

Ketika recovery bot mendekat dan chunk loaded kembali:

timer kembali berjalan.

8. RECOVERY URGENCY
============================================================

Recovery Scheduler menggunakan:

remainingDespawnTicks

Contoh:

Death A:

Death B:
remaining = 3200 ticks

Death C:
remaining = 5200 ticks

Priority:

1. Death A
2. Death B
3. Death C

============================================================
9. CHUNK UNLOAD BEHAVIOR
============================================================

Jika death chunk diperkirakan unload:

status:

TIMER_PAUSED_ESTIMATED

Tidak perlu mengirim bot yang tidak berguna ke lokasi.

Karena bot yang mendekati area bisa membuat chunk aktif kembali.

Flow:

DEATH_DROP
    |
    v
Is Chunk Active?
   / \
 YES  NO
 |     |
 v     v
URGENT TIMER_PAUSED
 |     |
 v     v
Recover Plan First

============================================================
11. TIGA KELAS RECOVERY
============================================================

REQUIRED
--------

Item harus dicari.

Recovery belum dianggap selesai jika item REQUIRED belum terverifikasi.

Contoh:
- diamond
- netherite
- enchanted gear
- important logistics cargo
- task critical material


OPTIONAL
--------

Ambil hanya jika:
- dekat
- inventory masih cukup
- tidak menambah risiko besar

Contoh:
- wood
- coal
- food berlebih
- common resources


IGNORE
------

Tidak perlu dicari.

Contoh default:
- dirt
- rotten_flesh
- junk
- low-value item

18. RECOVERY VALUE VS COST
============================================================

TravelDistance

+ BotWorkload

RecoveryValue - RecoveryCost

71. PRINSIP ARSITEKTUR
============================================================

1.
LLM tidak mengontrol Mineflayer secara langsung.

2.
Death recovery deterministic secara default.

3.
Tidak setiap death membutuhkan recovery.

4.
Tidak setiap item layak direcover.

5.
Item value harus dynamic.

6.
Current demand harus mempengaruhi value.

7.
Current task harus mempengaruhi value.

8.
Logistics cargo harus mendapat prioritas.

9.
Recovery cost harus diperhitungkan.

10.
Danger dapat membatalkan recovery.

11.
Recovery harus bounded.

12.
Tidak boleh terjadi infinite recovery loop.

13.
Reservation tidak dilepas sampai cargo benar-benar
dipastikan recovered atau lost.

14.
Recovery harus terverifikasi dengan inventory delta.

15.
Temporary DEATH_DROP memory harus dibersihkan.

16.
Death history tetap dipertahankan sebagai experience.

17.
Dropped item lifetime tidak boleh ditentukan hanya
dengan wall-clock 5 menit.

18.
Chunk activity sebaiknya dipertimbangkan.

19.
Recovery system harus menjadi failsafe untuk
Automatic Item Supply.

20.
Core tetap tidak boleh menerima raw Mineflayer client.
