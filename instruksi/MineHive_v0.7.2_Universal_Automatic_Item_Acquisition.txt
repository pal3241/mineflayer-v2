============================================================
1. VISI UTAMA 0.7.2
============================================================

Prinsip utama:

"Task menyatakan apa yang dibutuhkan.
MineHive menentukan bagaimana mendapatkannya."

Task tidak perlu mengetahui:
- item ada di inventory atau tidak
- chest mana yang menyimpan item
- bot lain mana yang punya item
- item perlu dicraft atau tidak
- bahan crafting tersedia atau tidak
- item perlu dismelt atau tidak
- resource perlu dicari sendiri atau tidak

Task hanya mendeklarasikan requirement.

Contoh:

TASK:
mine stone x64

Requirement:
PICKAXE
minimum tier sesuai rule

MineHive akan mencoba:

1. Inventory sendiri
2. Registered Storage
3. Bot lain yang punya surplus
4. Craft
5. Acquire bahan crafting
6. Smelt / Produce
7. Collect resource
8. Fail dengan alasan jelas

Jika item berhasil diperoleh:
task awal otomatis dilanjutkan.

11. SHAREABLE ITEM POLICY
============================================================

Bot tidak boleh memberikan item penting secara sembarangan.

Item SHAREABLE jika:
- bukan reserved cargo
- bukan satu-satunya required tool untuk current task
- bukan emergency food reserve
- bukan armor/weapon penting untuk current task
- jumlah setelah transfer masih >= donor minimum reserve
- donor tidak sedang membutuhkan item tersebut
- donor tidak berada dalam critical task stage

Contoh:
Bot2 iron_pickaxe x1, sedang mining -> NOT SHAREABLE
Bot2 iron_pickaxe x3, idle -> SHAREABLE x2

42. IMPORTANT TESTS
============================================================

1. Craft iron_pickaxe, iron missing, storage has iron -> retrieve then craft.
2. Mine stone, no pickaxe, storage has pickaxe -> retrieve and resume.
3. Storage empty, idle bot has spare pickaxe -> handoff and resume.
4. No pickaxe anywhere, materials exist -> craft and resume.
5. Missing crafting ingredients -> recursively acquire ingredients.
6. Need iron, only raw iron + fuel -> smelt then continue.
7. Need log, nowhere available except world -> collect fallback.
8. Donor has only one critical tool -> NOT SHAREABLE.
9. Donor has spare rare tool -> lease and return.
10. Acquisition cost absurd for tiny task -> reject expensive plan.
11. Dependency cycle -> DEPENDENCY_CYCLE.
12. Dependency too deep -> DEPENDENCY_DEPTH_EXCEEDED.
13. Multiple requirements -> batch acquisition.
14. Duplicate same-item needs -> merge/dedup.
15. Bot dies during acquisition -> 0.7.1 recovery, reacquire only shortage.

45. PRINSIP ARSITEKTUR
============================================================

1. Task menyatakan WHAT, bukan HOW.
2. Acquisition Service menentukan HOW.
3. Core tidak boleh mengakses raw Mineflayer API.
4. Existing handoff logic harus direuse.
5. Existing Task Queue menjadi executor dependency.
6. Storage dicoba sebelum mengambil item dari bot lain.
7. Bot donor hanya memberi resource shareable.
8. Tool tidak harus exact item jika category cukup.
9. Rare tool dipreservasi.
10. Recursive dependency harus bounded.
11. Cycle harus terdeteksi.
12. Acquisition harus diverifikasi.
13. Main task tidak langsung gagal jika requirement bisa diperoleh.
14. Main task harus bisa pause dan resume.
15. 0.7.1 menjadi failsafe acquisition saat bot mati.
16. Permanent loss hanya memicu reacquisition shortage.
17. LLM bukan eksekutor acquisition.
18. Acquisition default deterministic.
19. Universal Acquisition harus reusable oleh seluruh MineHive.
