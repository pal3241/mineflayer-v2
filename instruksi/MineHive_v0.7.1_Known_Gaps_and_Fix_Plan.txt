MINEHIVE v0.7.1 — INTELLIGENT DEATH RECOVERY
KNOWN GAPS / FIX PLAN
============================================================

Project:
MineHive / mineflayer-v2

Target:
Perbaikan dan hardening setelah release 0.7.1

Tujuan:
Mencatat masalah/gap yang ditemukan setelah review implementasi 0.7.1
agar dapat diperbaiki nanti tanpa kehilangan konteks.

============================================================
1. KONDISI UMUM
============================================================

0.7.1 sudah memiliki:
- death manifest
- item value evaluator
- REQUIRED / OPTIONAL / IGNORE
- dynamic item value
- recovery score
- despawn budget
- chunk-aware estimated timer
- recovery bot selector
- recovery state machine
- max attempts
- verification
- partial recovery
- reconciliation
- transfer takeover model
- recovery dashboard
- recovery API settings
- unit tests
- MineflayerAdapter death state capture

Gap utama:
RECOVERY ENGINE sudah ada,
tetapi FULL END-TO-END AUTOMATIC WORLD RECOVERY masih perlu dipastikan/hardening.

============================================================
2. GAP UTAMA — DEATH EVENT ORCHESTRATION
============================================================

MineflayerAdapter sudah emit death dengan:
- last alive state
- position
- dimension
- inventory snapshot
- cause
- keepInventory
- detectedAt

Yang harus dipastikan otomatis:

death event
-> Death Manifest
-> Logistics Death Context
-> Item Evaluation
-> Recovery Job
-> Bot Selection
-> Recovery Task
-> Execution
-> Verification
-> Reconciliation
-> Cleanup

============================================================
3. TARGET FIX — DEATH RECOVERY ORCHESTRATOR
============================================================

Suggested module:
src/logistics/recovery/death-recovery-orchestrator.js

Responsibilities:
- attach ke runtime bot
- listen death event
- capture death context
- create death manifest
- ask logistics.deathContext()
- merge logistics cargo
- evaluate items
- skip junk-only death
- mark logistics RECOVERY_REQUIRED
- create recovery job
- select recovery bot
- enqueue recovery task
- monitor execution
- verify
- reconcile
- cleanup memory

============================================================
4. TARGET FLOW
============================================================

REAL BOT DEATH
-> adapter.emit('death')
-> DeathRecoveryOrchestrator
-> createDeathManifest()
-> logistics.deathContext()
-> evaluateRecoveryItems()

If RECOVER:
markDeathRecovery()
-> create recovery job
-> select bot
-> Task Queue
-> navigate
-> search
-> collect
-> verify
-> reconcile
-> cleanup

If IGNORE:
record death episode
-> cleanup operational state

============================================================
5. GAP — RECOVERY EXECUTOR END-TO-END
============================================================

Primitive adapter sudah mendukung:
- navigation
- dropped item search
- dropped item collection
- inventory verification

Perlu executor yang menyatukan:
ASSIGNED
-> TRAVELLING
-> SEARCHING
-> COLLECTING
-> VERIFYING
-> RECOVERED

Suggested:
recovery-executor.js

============================================================
6. GAP — TASK QUEUE INTEGRATION
============================================================

Recovery sebaiknya memakai Task Queue untuk:
- navigation
- search
- collect
- verification
- retry
- timeout
- cancellation

Recovery Job = domain lifecycle.
Task Queue = executor.

============================================================
7. GAP — REAL BOT ASSIGNMENT
============================================================

Recovery Bot Selector sudah ada.
Pastikan result selector benar-benar digunakan untuk:
recovery.assign()
+ enqueue recovery task

REASSIGN_REQUIRED harus memicu selector lagi.

============================================================
8. GAP — SELF RECOVERY
============================================================

Original bot boleh recovery setelah respawn jika score terbaik.

Saat mati:
alive=false -> reject.

Setelah respawn:
alive=true -> eligible lagi.

============================================================
9. GAP — KEEP INVENTORY
============================================================

Jika keepInventory enabled:
- jangan buat item recovery job
- jangan mark cargo lost
- death episode tetap boleh dicatat

Jika unknown:
gunakan conservative handling.

============================================================
10. GAP — CHUNK TIMER ESTIMATION
============================================================

Perlu hardening terhadap:
- double advancing
- restart
- stale chunk status
- server tick mismatch

Suggested fields:
lastObservedServerTick
lastChunkActive
timerUpdatedAt

============================================================
11. GAP — RESTART RECOVERY
============================================================

Test restart saat status:
ASSIGNED
TRAVELLING
SEARCHING
COLLECTING
VERIFYING

Expected:
- job restored
- stale assignment revalidated
- recovery resumes/reassigns
- despawn budget tidak double-count

============================================================
12. GAP — ITEM ENTITY MATCHING
============================================================

Handle:
- multiple stacks item sama
- item merge
- item split
- water movement
- pickup by other entity/player
- entity id changes
- partial missing

Verification harus inventory-based, bukan entity-based saja.

============================================================
13. GAP — PARTIAL RECOVERY ORCHESTRATION
============================================================

VERIFYING
-> PARTIAL
-> reconcile
-> PARTIAL_RECONCILED
-> cleanup

REQUIRED loss = permanent loss.
OPTIONAL loss = optional not recovered.

============================================================
14. GAP — LOGISTICS RESERVATION PROTECTION
============================================================

Death during transfer:
reservation jangan RELEASED terlalu awal.

Use:
RECOVERY_REQUIRED

Final only after:
RECOVERED
atau
PERMANENT_LOSS

============================================================
15. GAP — TRANSFER TAKEOVER EXECUTION
============================================================

Model sudah punya TAKEOVER_REQUIRED.
Perlu executor nyata:

Recovery Bot
-> recovered cargo
-> take over transfer
-> continue destination
-> verify delivery

Alternative:
return cargo to storage.

============================================================
16. GAP — RECOVERY HEALTH STATUS
============================================================

Normal active recovery tidak seharusnya otomatis membuat application DEGRADED.

Suggested:
HEALTHY:
- active recovery normal
- progress berjalan
- attempts rendah

DEGRADED:
- urgent despawn
- repeated failure
- stuck
- no valid bot
- queue saturation

============================================================
17. GAP — DASHBOARD RECOVERED ITEM KPI
============================================================

Jangan hitung semua manifest items sebagai recovered.

Example:

Recovered:
diamond x4

Not 68.

Gunakan verification.items[].recoveredCount.

18. GAP — PERMANENT LOSS KPI
============================================================

Jangan anggap semua item failed job sebagai permanent loss.

Bedakan:
- REQUIRED permanent loss
- OPTIONAL not recovered
- IGNORE junk

- replay

- leased tool

- junk only
- no strategic value

53. RELATION TO 0.7.2
============================================================

0.7.2 Universal Automatic Item Acquisition akan bergantung pada 0.7.1 sebagai failsafe.

Acquisition
-> bot acquires item
-> bot dies
-> 0.7.1 Recovery

Recovered:
resume acquisition

Permanent loss:
reacquire shortage only

0.7.1 tidak harus langsung selesai sebelum desain 0.7.2 dibuat,
tetapi gap end-to-end sebaiknya ditutup sebelum 0.7.2 dianggap production-ready.
